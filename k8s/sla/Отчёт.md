# Отчёт: SLI, SLO и SLA приложения URL Shortener

На метриках из прошлого задания (VictoriaMetrics single в minikube, service discovery по аннотациям) сформулированы
SLI, SLO и SLA приложения, добавлены пробер и управляемая деградация (chaos) для демонстрации. 
## 1. Подходы

- RBSLO (request based) - доля успешных операций среди всех: `хорошие запросы / все запросы` за окно.
- TBSLO (time based) - доля «хороших» минут: минута хорошая, если в ней SLI не ниже SLO. Для общего SLA минута
  хорошая, только если выполнены все SLO одновременно.

В работе используются оба: SLI считаются как RBSLO по минутным окнам, SLA - в двух вариантах (доля хороших минут и
доля хороших запросов за период), общий SLA - как TBSLO.

## 2. Используемые метрики

| Метрика | Тип | Что используется | SLI |
|---|---|---|---|
| `http_request_duration_seconds_count` | histogram (число запросов) | метки `route`, `status` | 1 - доступность; знаменатель для 2 и 3 |
| `http_request_duration_seconds_bucket` | histogram (бакеты) | `le="0.25"` для `route="/r/:code"`, `le="0.5"` для `POST /api/v1/links` | 2 - скорость редиректа, 3 - скорость создания |
| `urlshort_prober_runs_total` | counter | метка `result="success\|failure"` | 4 - успешность сценария пробера |

Все метрики backend суммируются по двум репликам (`sum`), запросы проб Kubernetes (`/healthz`, `/readyz`) из SLI
исключены: это не пользовательский трафик.

## 3. Пробер

Пробер - синтетический пользователь. Запускается через аргумент `probe` того же бинарника backend (`serve`, `migrate`,
`probe`).

Раз в 10 секунд (`PROBER_INTERVAL`) он выполняет сценарий через **frontend** (`PROBER_TARGET_URL=http://frontend`) -
весь путь пользователя: nginx → backend → PostgreSQL:

1. `POST /api/v1/links` - создать ссылку, ожидается 201;
2. `GET /r/{code}` - перейти по ней, ожидается 302 и `Location`, равный исходному URL;
3. `DELETE /api/v1/links/{id}` - удалить, ожидается 204 (выполняется и после неудачного перехода, чтобы не копить
   мусор в базе).

Прогон успешен, только если все шаги прошли. Таймаут запроса - 3 секунды (`PROBER_TIMEOUT`). HTTP-клиент
сгенерирован oapi-codegen из той же `openapi.yaml`, что и сервер (`client: true`).

Метрики пробера собираются тем же service discovery: аннотации `prometheus.io/*` на поде, порт 9090.

## 4. SLI, SLO и SLA

| # | SLI | Формула SLI (окно 1 мин) | SLO | SLA (TBSLO): доля минут периода, когда SLO выполнен | SLA (RBSLO): доля хороших событий за период |
|---|---|---|---|---|---|
| 1 | Доступность API | запросы без 5xx / все запросы | ≥ 99 % | ≥ 95 % | ≥ 99 % запросов |
| 2 | Скорость редиректа | редиректы `/r/:code` быстрее 250 мс / все редиректы | ≥ 95 % | ≥ 95 % | ≥ 95 % редиректов |
| 3 | Скорость создания ссылки | `POST /api/v1/links` быстрее 500 мс / все создания | ≥ 95 % | ≥ 95 % | ≥ 95 % созданий |
| 4 | Успешность сценария пробера | успешные прогоны / все прогоны | ≥ 99 % | ≥ 95 % | ≥ 99 % прогонов |
| - | **Общий SLA** | минута хорошая, если выполнены SLO 1-4 одновременно | - | **≥ 90 %** минут | - |

Формулировки:
- **SLO 1:** за каждую минуту не менее 99 % запросов к API завершаются без серверной ошибки (5xx).
- **SLO 2:** за каждую минуту не менее 95 % переходов по коротким ссылкам выполняются быстрее 250 мс.
- **SLO 3:** за каждую минуту не менее 95 % созданий ссылок выполняются быстрее 500 мс.
- **SLO 4:** за каждую минуту не менее 99 % прогонов пробера успешны. При 6 прогонах в минуту это значит, что минута
  хорошая, только если все прогоны прошли.
- **SLA приложения:** в течение месяца (в демонстрации - часа) каждый SLO выполняется не менее 95 % минут, а все
  SLO одновременно - не менее 90 % минут.

**Минута без данных.** Если в минуту пробер работал, а данных SLI нет, минута считается **плохой**: трафик пробера
был, значит, отсутствие данных - это недоступность (например, все поды backend не готовы и запросы до них не
доходят), а не отсутствие пользователей. Минуты, когда нет данных и у пробера (до развёртывания, пока пробер не
запущен), в расчёт **не входят**: в них нет наблюдения, и считать их плохими так же неверно, как хорошими. В запросах
это `or (sli4 * 0)`: значение 0 подставляется только там, где есть SLI пробера.

### Формулы

SLI (RBSLO) за окно `w`:

```
SLI = good(w) / total(w)
```

Хорошая минута для SLO `i` и общая хорошая минута:

```
good_minute_i = 1, если SLI_i(1m) >= SLO_i; 0, если SLI_i(1m) < SLO_i или данных нет, а пробер работал
good_minute   = good_minute_1 * good_minute_2 * good_minute_3 * good_minute_4
```

SLA (TBSLO) и SLA (RBSLO) за период `T`:

```
SLA_TB_i = Σ good_minute_i / число наблюдаемых минут в T
SLA_TB   = Σ good_minute   / число наблюдаемых минут в T
SLA_RB_i = good_i(T) / total_i(T)
```

Остаток бюджета ошибок (RBSLO): `1 - (1 - SLA_RB_i) / (1 - SLO_i)`. 1 - бюджет не тронут, 0 - израсходован, меньше
0 - SLO за период нарушен.

### Запросы MetricsQL

SLI (используются и в графиках, и внутри SLA):

```
SLI 1, доступность:
sum(rate(http_request_duration_seconds_count{app="backend", route!~"/healthz|/readyz", status!~"5.."}[1m]))
  / sum(rate(http_request_duration_seconds_count{app="backend", route!~"/healthz|/readyz"}[1m]))

SLI 2, скорость редиректа:
sum(rate(http_request_duration_seconds_bucket{app="backend", route="/r/:code", le="0.25"}[1m]))
  / sum(rate(http_request_duration_seconds_count{app="backend", route="/r/:code"}[1m]))

SLI 3, скорость создания:
sum(rate(http_request_duration_seconds_bucket{app="backend", route="/api/v1/links", method="POST", le="0.5"}[1m]))
  / sum(rate(http_request_duration_seconds_count{app="backend", route="/api/v1/links", method="POST"}[1m]))

SLI 4, пробер:
sum(rate(urlshort_prober_runs_total{result="success"}[1m])) / sum(rate(urlshort_prober_runs_total[1m]))
```

SLA (TBSLO) считаются подзапросом `[1h:1m]`: SLI вычисляется на каждую минуту часа, признак «хорошая минута»
усредняется. 

Общая часть запроса:

```
WITH (
  api = {app="backend", route!~"/healthz|/readyz"},
  redirect = {app="backend", route="/r/:code"},
  create = {app="backend", route="/api/v1/links", method="POST"},
  sli1 = sum(rate(http_request_duration_seconds_count{api, status!~"5.."}[1m])) / sum(rate(http_request_duration_seconds_count{api}[1m])),
  sli2 = sum(rate(http_request_duration_seconds_bucket{redirect, le="0.25"}[1m])) / sum(rate(http_request_duration_seconds_count{redirect}[1m])),
  sli3 = sum(rate(http_request_duration_seconds_bucket{create, le="0.5"}[1m])) / sum(rate(http_request_duration_seconds_count{create}[1m])),
  sli4 = sum(rate(urlshort_prober_runs_total{result="success"}[1m])) / sum(rate(urlshort_prober_runs_total[1m])),
  good(sli, slo) = (sli >= bool slo) or (sli4 * 0),
  good_minute = good(sli1, 0.99) * good(sli2, 0.95) * good(sli3, 0.95) * good(sli4, 0.99)
)
```

## 6. Изменения приложения для скринкаста

Для демонстрации в backend добавлена **управляемая деградация** - middleware `Chaos`
(`internal/controller/middleware/chaos.go`), настраиваемая переменными окружения (по умолчанию выключена):

| Переменная | По умолчанию | Действие |
|---|---|---|
| `CHAOS_ERROR_RATE` | `0` | доля запросов, на которые backend отвечает 500 (`0.1` - каждый десятый) |
| `CHAOS_LATENCY` | `0s` | дополнительная задержка каждого запроса (`400ms`) |

Middleware стоит после HTTP-метрик и access-лога, поэтому внедрённые ошибки и задержка попадают в метрики и логи как
настоящие (в логе у ошибки `"error":"chaos: injected failure"`). Пробы `/healthz` и `/readyz` не затрагиваются -
Kubernetes не перезапускает поды из-за деградации. При включении backend пишет в лог `chaos enabled`.

Сценарии и ожидаемый эффект:

| Сценарий | Команда | SLI 1 | SLI 2 | SLI 3 | SLI 4 |
|---|---|---|---|---|---|
| Ошибки 10 % | `kubectl set env deployment/backend -n url-shortener CHAOS_ERROR_RATE=0.1` | ~90 %, ниже SLO | в норме | в норме | ~73 % (0.9³: в прогоне три запроса), ниже SLO |
| Задержка 400 мс | `kubectl set env deployment/backend -n url-shortener CHAOS_LATENCY=400ms` | в норме | ~0 %, ниже SLO | в норме (400 мс < 500 мс) | в норме |
| Отказ базы | `kubectl scale statefulset postgres -n url-shortener --replicas=0` | 500, затем нет данных → плохая минута | нет данных → плохая минута | нет данных → плохая минута | 0 % |
| Возврат | `kubectl set env deployment/backend -n url-shortener CHAOS_ERROR_RATE- CHAOS_LATENCY-`, `kubectl scale statefulset postgres -n url-shortener --replicas=1` | восстанавливается | восстанавливается | восстанавливается | восстанавливается |

`kubectl set env` меняет Deployment и сам запускает rolling update (около 20 секунд, без простоя: `maxUnavailable: 0`).
Явная переменная в `env` перекрывает значение из ConfigMap. Суффикс `-` удаляет переменную, и снова действует `"0"`
из ConfigMap.
