# Отчёт: запуск URL Shortener в Kubernetes (minikube)

В этом задании сервис запускается в однонодовом кластере minikube.

**Окружение:** Windows 11, Docker Desktop, minikube v1.39.0 (драйвер `docker`, container runtime `docker`),
Kubernetes v1.37.0, kubectl v1.37.

## 1. Сборка образов

Dockerfile обоих сервисов уже были написаны в первом задании (`backend/Dockerfile`, `frontend/Dockerfile`).

- `minikube image load` - образ собирается в Docker Desktop, затем копируется на узел.
  Если образ уже собран после `docker-env`, этот шаг ничего не добавляет.
- Теги фиксированные (`1.0.0`), а не `latest`: для `latest` Kubernetes по умолчанию ставит
  `imagePullPolicy: Always` и пытается скачать образ из Docker Hub, где его нет. В манифестах стоит
  `imagePullPolicy: IfNotPresent` - использовать образ, уже лежащий на узле.

## 2. Использованные абстракции Kubernetes

Манифесты лежат в `k8s/`, номера в именах файлов задают порядок применения (`kubectl apply -f k8s/` читает файлы
по алфавиту, а Namespace должен быть создан раньше объектов внутри него).

| Файл | Объекты |
|---|---|
| `00-namespace.yml` | Namespace `url-shortener` |
| `01-configmap.yml` | ConfigMap `url-shortener-config` |
| `02-postgres.yml` | Service `postgres` (headless), StatefulSet `postgres` |
| `03-migrate-job.yml` | Job `migrate` |
| `04-backend.yml` | Deployment `backend`, Service `backend` (ClusterIP) |
| `05-frontend.yml` | Deployment `frontend`, Service `frontend` (NodePort) |
| создаётся командой | Secret `postgres-credentials` |

### Namespace
Все объекты приложения живут в отдельном пространстве имён `url-shortener`: они не смешиваются с объектами
в `default`, а всё приложение (включая диск базы) удаляется одной командой `kubectl delete namespace url-shortener`.

### ConfigMap и Secret
Конфигурация передаётся в контейнеры через переменные окружения (фактор III из первого задания), образ один
для любого окружения.

- **ConfigMap `url-shortener-config`** - несекретные настройки: `POSTGRES_HOST=postgres` (имя Service базы),
  `POSTGRES_PORT`, `POSTGRES_DB`, `HTTP_PORT`, `SHUTDOWN_TIMEOUT`, `LOG_LEVEL`.
- **Secret `postgres-credentials`** - `POSTGRES_USER` и `POSTGRES_PASSWORD`. Создаётся командой
  `kubectl create secret generic`, а не YAML-файлом, чтобы пароль не попал в репозиторий и архив.
  Имена ключей совпадают с переменными, которые ожидает и официальный образ PostgreSQL, и бэкенд, поэтому
  оба подключают секрет целиком через `envFrom`.

### StatefulSet + PersistentVolumeClaim (PostgreSQL)
База - приложение с состоянием, поэтому запускается через **StatefulSet**, а не Deployment:
- под получает стабильное имя `postgres-0`, которое сохраняется при пересоздании;
- по шаблону `volumeClaimTemplates` для пода создаётся свой **PVC** `data-postgres-0` (1Gi, `ReadWriteOnce`).
  StorageClass `standard` (по умолчанию в minikube) динамически создаёт под него **PersistentVolume** - каталог
  на узле. Диск монтируется в `/var/lib/postgresql/data`, данные лежат в подкаталоге `pgdata` (`PGDATA`);
- если под удалить, StatefulSet создаст его заново с тем же именем и подключит тот же PVC - данные сохраняются.

`replicas: 1`: PostgreSQL нельзя запустить в нескольких экземплярах на одних файлах, а увеличение `replicas` дало бы
вторую независимую пустую базу. Масштабирование базы - это репликация, а не `kubectl scale`.

Пробы: readiness и liveness выполняют `pg_isready`. Liveness начинается через 30 секунд, чтобы не убить контейнер
во время первичной инициализации базы.

### Headless Service `postgres`
Service с `clusterIP: None` не имеет виртуального IP: DNS-имя `postgres` сразу указывает на IP пода, а у пода
появляется постоянное имя `postgres-0.postgres`. Такой Service нужен StatefulSet (поле `serviceName`).
По умолчанию в DNS попадают только поды, прошедшие readiness, поэтому имя `postgres` начинает резолвиться
только после того, как база готова принимать подключения.

### Job (миграции)
Миграции схемы - разовая административная задача (фактор XII). **Job `migrate`** запускает тот же образ бэкенда
с аргументом `migrate`, применяет миграции и завершается.

- `restartPolicy: OnFailure` - если база ещё не готова, контейнер перезапускается в том же поде с растущей паузой;
- `backoffLimit: 10` и `activeDeadlineSeconds: 300` - предел числа попыток и общего времени, после которых
  Job считается неуспешным;
- миграции идемпотентны (goose хранит версию схемы в базе), повторный запуск безопасен.

### Deployment (backend и frontend)
Бэкенд и фронтенд не хранят состояния (фактор VI), поэтому запускаются через **Deployment** (он управляет
ReplicaSet, а тот - подами) в двух репликах и масштабируются командой `kubectl scale`.

- **Стратегия `RollingUpdate`** с `maxSurge: 1` и `maxUnavailable: 0`: при обновлении образа сначала поднимается
  новый под и только после прохождения readiness удаляется старый, число работающих реплик не уменьшается.
- **Пробы бэкенда:** readiness `/readyz` проверяет соединение с базой - если база недоступна, под убирается
  из Service и не получает трафик. Liveness `/healthz` от базы не зависит: падение базы не должно приводить к
  перезапускам бэкенда.
- **Пробы фронтенда:** обе на `/healthz`, на который nginx отвечает сам.
- **`resources`:** `requests` - гарантированный минимум CPU и памяти, по нему планировщик выбирает узел;
  `limits` - потолок (при превышении памяти контейнер получает `OOMKilled`, CPU притормаживается).
- Порты контейнеров именованы (`http`), Service и пробы ссылаются на порт по имени.

### Service ClusterIP `backend`
Постоянный виртуальный IP и DNS-имя `backend` внутри кластера. kube-proxy распределяет соединения между
подами бэкенда, прошедшими readiness. Снаружи кластера недоступен - к API ходит только фронтенд.

### Service NodePort `frontend`
Открывает UI снаружи: на каждом узле открывается порт `30080` (`nodePort`), запросы на него уходят на поды
фронтенда (порт контейнера 80). Изнутри кластера тот же Service доступен как `frontend:80`.

## 3. Взаимодействие сервисов

```
браузер
   │  minikube service → 127.0.0.1:<порт> → узел:30080 (NodePort)
   ▼
Service frontend (NodePort 30080, port 80)
   ▼
поды frontend ×2 (nginx :80)
   │  /           → статика React
   │  /api/*, /r/* → proxy_pass http://backend:8080
   ▼
Service backend (ClusterIP, port 8080)
   ▼
поды backend ×2 (Go :8080)
   │  postgres:5432 (из ConfigMap: POSTGRES_HOST, POSTGRES_PORT)
   ▼
Service postgres (headless) → под postgres-0 (:5432) → PVC data-postgres-0

Job migrate (тот же образ бэкенда, команда migrate) → postgres:5432 → применяет схему и завершается
```

| Откуда | Куда | Адрес | Как находит |
|---|---|---|---|
| браузер | frontend | `127.0.0.1:<порт>` → узел `:30080` | туннель `minikube service` + NodePort |
| frontend (nginx) | backend | `http://backend:8080` | переменная `BACKEND_URL` в Deployment, DNS-имя Service |
| backend | PostgreSQL | `postgres:5432` | `POSTGRES_HOST`/`POSTGRES_PORT` из ConfigMap, DNS-имя headless Service |
| Job migrate | PostgreSQL | `postgres:5432` | те же ConfigMap и Secret |
| все поды | CoreDNS | `10.96.0.10:53` | короткие имена (`backend`, `postgres`) дополняются доменом `url-shortener.svc.cluster.local` |
