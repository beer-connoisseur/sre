# Стратегии деплоя: Gateway API (Envoy Gateway) + minikube

Демонстрация пяти стратегий обновления приложения на своём сервисе (URL Shortener) в локальном
minikube: **Rolling**, **Blue/Green**, **Canary**, **A/B**, **Shadow**. Трафик между версиями
дробит **Gateway API** (`HTTPRoute` на Envoy Gateway), а не Ingress и не service mesh.

## Быстрый старт (с нуля)

```bash
# 1. собрать образы двух версий и загрузить в minikube
docker build -t url-shortener-backend:1.0.0 --build-arg VERSION=1.0.0 ../backend
docker build -t url-shortener-backend:2.0.0 --build-arg VERSION=2.0.0 ../backend
minikube image load url-shortener-backend:1.0.0 url-shortener-backend:2.0.0

# 2. базовое приложение + секрет
kubectl apply -f ..                      # 00-06: ns, config, postgres, migrate, backend, frontend, prober
kubectl -n url-shortener create secret generic postgres-credentials \
  --from-literal=POSTGRES_USER=shortener --from-literal=POSTGRES_PASSWORD=...

# 3. мониторинг (если ещё нет)
helm upgrade --install vm-single vm/victoria-metrics-single -n monitoring --create-namespace \
  -f ../monitoring/vmsingle-values.yaml --wait
helm upgrade --install grafana grafana/grafana -n monitoring \
  -f ../grafana/grafana-values.yaml --set adminPassword=admin --wait

# 4. Envoy Gateway + Gateway
kubectl apply --server-side -f https://github.com/envoyproxy/gateway/releases/download/v1.10.0/install.yaml
kubectl wait -n envoy-gateway-system deployment/envoy-gateway --for=condition=Available
kubectl apply -f gateway.yml

# 5. дашборд «Deployment Strategies» (uid deploy-strategies) — импорт в Grafana:
#    Dashboards → Import → загрузить monitoring/deploy-strategies-dashboard.json (источник VictoriaMetrics)
kubectl port-forward -n monitoring svc/grafana 3001:80   # admin / admin
```

Дальше — по одной стратегии за раз. Перед каждой: `./reset.sh`. Трафик: `./traffic.sh`
(сам найдёт Envoy-прокси, пробросит `:8888` и будет печатать версию, которая ответила).

---

## Стратегия 1 — Rolling (постепенное переключение)

Один Deployment `backend`, Kubernetes сам заменяет поды по одному. Gateway API не дробит
трафик — HTTPRoute всегда смотрит на Service `backend`.

```bash
./reset.sh
kubectl apply -f rolling/01-backend-v1.yml       # Deployment(3 реплики, 1.0.0) + Service + HTTPRoute
kubectl -n url-shortener rollout status deployment/backend

./traffic.sh                                     # в другом терминале: только 1.0.0
kubectl apply -f rolling/02-backend-v2.yml       # image 2.0.0, метка version на подах
kubectl -n url-shortener rollout status deployment/backend
kubectl get pods -n url-shortener -l app=backend -w   # поды заменяются по одному

# откат
kubectl -n url-shortener rollout undo deployment/backend
```

## Стратегия 2 — Blue/Green (мгновенное переключение и откат)

Обе версии подняты одновременно; переключение — одним apply другого HTTPRoute.

```bash
./reset.sh
kubectl apply -f blue-green/backend-v1.yml -f blue-green/backend-v2.yml   # green + blue по 3 реплики
kubectl apply -f blue-green/httproute-green.yml   # весь трафик на 1.0.0
./traffic.sh                                      # только 1.0.0

kubectl apply -f blue-green/httproute-blue.yml    # МГНОВЕННО 100% на 2.0.0
kubectl apply -f blue-green/httproute-green.yml   # мгновенный откат на 1.0.0
```

## Стратегия 3 — Canary (рампа 90/10 → 50/50 → 0/100)

Веса в `backendRefs` одного HTTPRoute; обе версии подняты (файлы из blue-green).

```bash
./reset.sh
kubectl apply -f blue-green/backend-v1.yml -f blue-green/backend-v2.yml

kubectl apply -f canary/httproute-90-10.yml      # v2 ~10%
kubectl apply -f canary/httproute-50-50.yml      # v2 ~50%
kubectl apply -f canary/httproute-0-100.yml      # v2 100%
```

Замечание про ресурсы: на шаге 90/10 три реплики v2 для 10% трафика избыточны — в деме
реплики фиксированы ради простоты. Реальные canary-контроллеры (Argo Rollouts, Flagger)
масштабируют набор подов пропорционально весу или заводят отдельный маленький canary-Deployment.

## Стратегия 4 — A/B (по заголовку на выбранную аудиторию)

Не случайные проценты, а точно выбранная публика — здесь по заголовку `x-user-group: beta`.

```bash
./reset.sh
kubectl apply -f blue-green/backend-v1.yml -f blue-green/backend-v2.yml
kubectl apply -f ab/httproute-ab.yml

./traffic.sh                                    # все — 1.0.0
HDR='x-user-group: beta' ./traffic.sh           # все — 2.0.0
```

Явные проверки (порт `:8888` уже проброшен запущенным `traffic.sh`):

```bash
curl -s -D - -o /dev/null http://localhost:8888/healthz | grep -i x-version
# x-version: 1.0.0
curl -s -D - -o /dev/null -H 'x-user-group: beta' http://localhost:8888/healthz | grep -i x-version
# x-version: 2.0.0
```

## Стратегия 5 — Shadow (зеркалирование трафика)

Пользователю отвечает 1.0.0, а копия каждого запроса уходит на 2.0.0 (её ответ отбрасывается).

```bash
./reset.sh
kubectl apply -f blue-green/backend-v1.yml -f blue-green/backend-v2.yml
kubectl apply -f shadow/httproute-shadow.yml

./traffic.sh                                          # всегда X-Version: 1.0.0
kubectl logs -n url-shortener deployment/backend-v2 --tail=20   # но сюда приходит тот же трафик
```
