# Отчёт: URL Shortener

## 1. Доменная область

Сервис коротких ссылок. Пользователь вставляет длинный адрес, получает короткую ссылку вида
`http://<host>/r/<code>` и делится ею. При переходе по короткой ссылке сервис перенаправляет
на исходный адрес и увеличивает счётчик переходов.

Через веб-интерфейс можно:

- создать ссылку со случайным кодом или со своим (`/r/seminar-1`);
- посмотреть список ссылок с количеством переходов;
- изменить адрес назначения или код (короткая ссылка продолжает работать, а ведёт уже на новый адрес);
- удалить ссылку.

Проект основан на моём пет-проекте [url-shortener](https://github.com/beer-connoisseur/url-shortener),
доработанном под задание.

## 2. Стек

| Компонент | Технологии                                                                                                                                                                                                                                                                                                                                                                                                 |
|---|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Бэкенд | Go 1.26, `gin` (HTTP-сервер), `oapi-codegen` (модели, интерфейс сервера и роутинг из OpenAPI), `kin-openapi` + `gin-middleware` (валидация запросов по спецификации), `pgx/v5` (драйвер и пул соединений), `goose` (миграции), `caarlos0/env` (конфиг из переменных окружения), `urfave/cli/v3` (команды `serve` / `migrate`), `zap` + `gin-contrib/zap` (структурированные JSON-логи, включая access-лог) |
| Фронтенд | React 18, TypeScript, Vite; в контейнере статика раздаётся через nginx                                                                                                                                                                                                                                                                                                                                     |
| СУБД | PostgreSQL 17                                                                                                                                                                                                                                                                                                                                                                                              |
| Окружение | Docker, Docker Compose                                                                                                                                                                                                                                                                                                                                                                                     |

## 3. Сущности доменной области

### Link (таблица `shortener.links`)

| Поле | Тип | Описание |
|---|---|---|
| `id` | `UUID` | Идентификатор, генерируется базой (`gen_random_uuid()`) |
| `code` | `VARCHAR(32)`, `UNIQUE` | Код короткой ссылки: 3–32 символа `[A-Za-z0-9_-]`. Случайный (8 символов, `crypto/rand`) или заданный пользователем |
| `original_url` | `TEXT` | Адрес назначения, только абсолютный `http`/`https`, до 2048 символов |
| `clicks` | `BIGINT` | Количество переходов |
| `created_at` / `updated_at` | `TIMESTAMPTZ` | Время создания и последнего изменения |

### CRUD-операции

| Операция | HTTP | 
|---|---|
| Create | `POST /api/v1/links` | 
| Read | `GET /api/v1/links/{id}`, `GET /api/v1/links?limit&offset` |
| Update | `PATCH /api/v1/links/{id}` |
| Delete | `DELETE /api/v1/links/{id}` |

Плюс `GET /r/{code}` (редирект) и пробы `GET /healthz`, `GET /readyz`.

## 4. Соответствие 12 факторам

### I. Кодовая база

Одна кодовая база под контролем версий (Git), из неё собираются и разворачиваются все окружения;
окружения различаются только переменными окружения, а не ветками или копиями кода.

Репозиторий содержит два деплоящихся компонента, `backend/` и `frontend/` (монорепозиторий). Строго по
методологии это два приложения, и каждому положен свой репозиторий. Я оставил их вместе, потому что
это одна система с общим жизненным циклом и контрактом API. При этом соблюдена суть фактора:
у компонентов нет общего кода, у каждого свой манифест зависимостей, свой Dockerfile и свой
контекст сборки, собираются и версионируются они независимо. Если компоненты начнут развиваться
разными командами, их можно разнести по двум репозиториям без изменений в коде.

### II. Зависимости

- Все зависимости объявлены явно и зафиксированы: `backend/go.mod` + `go.sum` (с контрольными суммами),
  `frontend/package.json` + `package-lock.json`.
- Сборка воспроизводима одной командой: `go mod download` / `npm ci` ставят ровно зафиксированные версии.
- Изоляция: сборка и запуск идут в контейнерах. Бинарник бэкенда статический (`CGO_ENABLED=0`) и
  запускается в образе `distroless/static` без shell и системных утилит, поэтому приложение
  физически не может неявно полагаться на что-то, установленное в системе (как `curl` в примере с семинара).
- Даже миграции встроены в бинарник (`go:embed`), бинарнику не нужны файлы рядом.
- Инструменты разработки тоже зафиксированы: генератор `oapi-codegen` подключён через директиву `tool`
  в `go.mod`, поэтому `go generate` у всех запускает одну и ту же версию, ставить его глобально не нужно.

### III. Конфигурация

- Вся конфигурация читается из переменных окружения (`backend/internal/config/config.go`), в коде нет
  адресов, паролей и параметров окружений.
- У секретов (`POSTGRES_USER`, `POSTGRES_PASSWORD`) нет значений по умолчанию: без них сервис не стартует
  с понятной ошибкой `invalid config: required environment variable "POSTGRES_USER" is not set`,
  а не подключается молча с «дефолтным» паролем.
- Фронтенд не вшивает адрес бэкенда в сборку: он обращается к относительному пути `/api`, а адрес бэкенда
  подставляется в конфиг nginx при старте контейнера из переменной `BACKEND_URL` (механизм `templates`
  официального образа nginx). Один и тот же образ фронтенда работает в любом окружении.
- `.env` с реальными значениями исключён из репозитория (`.gitignore`), в репозитории только `.env.example`.

### IV. Сторонние службы (backing services)

PostgreSQL - подключаемый ресурс: адрес, база, пользователь, пароль и `sslmode` задаются переменными.
Локальный контейнер Postgres заменяется управляемой базой в облаке изменением переменных, без пересборки
и изменений в коде.

Код работает с базой через интерфейс репозитория (`linkRepository` в usecase), бизнес-логика не знает о SQL.
### V. Сборка, релиз, выполнение

Этапы разделены:

- **Сборка**: `docker build` превращает код в неизменяемый образ. Многоэтапный Dockerfile: компиляция
  в `golang`/`node`, в итоговый образ попадает только бинарник или статика.
- **Релиз** = образ + конфигурация окружения. Образ получает идентификатор (`APP_VERSION` → тег образа
  `url-shortener-backend:<версия>`), версия вшивается в бинарник (`-ldflags -X main.version`) и пишется
  в каждую строку лога, так что по логам видно, какой релиз обработал запрос.
- **Выполнение**: контейнер запускается с конфигурацией из окружения. На этапе выполнения код не меняется,
  ничего не собирается и не правится руками.

Откат - запуск образа с предыдущим тегом. Миграции пишутся совместимыми с предыдущей версией кода,
чтобы откат приложения не требовал отката схемы.

### VI. Процессы

Бэкенд stateless: между запросами в памяти процесса ничего не хранится (нет сессий, кэшей, счётчиков,
загруженных файлов). Всё состояние, включая счётчик переходов, лежит в PostgreSQL. Фронтенд - статика, состояния у него нет.

### VII. Привязка портов (port binding)

Бэкенд - самодостаточный HTTP-сервер из стандартной библиотеки Go: он сам слушает порт `HTTP_PORT`
и не требует внешнего веб-сервера или контейнера приложений. Фронтенд экспортирует свой сервис через
nginx на порту 80. nginx здесь - часть компонента «фронтенд» (раздача статики и прокси), а не
обязательная прослойка для запуска бэкенда: бэкенд одинаково работает и за nginx, и напрямую.

### VIII. Параллелизм

Масштабирование горизонтальное: бэкенд stateless, поэтому можно запустить
сколько угодно одинаковых реплик.
Порт бэкенда специально не публикуется на хост, чтобы реплики не конфликтовали.

Типы процессов разделены: `serve` обрабатывает HTTP-запросы, `migrate` - разовая задача.
Внутри процесса конкурентность обеспечивает HTTP-сервер (горутина на запрос) и пул соединений к базе.

### IX. Утилизируемость (disposability)

- **Быстрый старт**: сервис стартует за миллисекунды. Пул соединений создаётся лениво, прогрева кэшей нет,
  миграции вынесены из старта. Готовность принимать трафик сообщает `/readyz` (есть ли соединение с базой),
  а `/healthz` - что процесс жив (не зависит от базы, чтобы недоступность базы не приводила к бессмысленным
  перезапускам сервиса).
- **Корректное завершение**: по SIGTERM/SIGINT сервис перестаёт принимать новые соединения, дожидается
  завершения текущих запросов (`http.Server.Shutdown`, не дольше `SHUTDOWN_TIMEOUT`) и закрывает пул
  соединений к базе.
- **Устойчивость к внезапной смерти**: если процесс убит без предупреждения, данные не теряются. Каждая
  операция - одна транзакция в базе, а счётчик переходов обновляется атомарно.

### X. Паритет разработки и продакшена

- Локальное окружение (`docker compose`) использует те же образы и ту же версию PostgreSQL (17), что и
  остальные окружения. Нет подмен вроде «SQLite локально, Postgres на проде».
- Окружения отличаются только переменными окружения и ресурсами.
- Поднять полное окружение с нуля можно одной командой `docker compose up -d --build`. Новому разработчику
  не нужны ни Go, ни Node, ни Postgres на машине - только Docker.

### XI. Журналирование

Приложение пишет логи как поток событий в stdout и ничего не знает о том, куда они попадут дальше:
в файлы, в Loki или в Elasticsearch - решает окружение. Бэкенд пишет структурированные JSON-логи через zap:
события приложения (старт, остановка, ошибки, итог миграций) и access-лог - по строке на каждый HTTP-запрос
(middleware `ginzap`: статус, метод, путь, query, IP клиента, user-agent, длительность). Паники тоже
перехватываются и логируются через zap (`ginzap.RecoveryWithZap`). В каждой строке есть версия релиза,
поэтому логи удобно разбирать и фильтровать по полям в системе сбора.
Уровень логирования задаётся переменной `LOG_LEVEL`. nginx в официальном образе тоже пишет логи в stdout/stderr.

### XII. Административные процессы

Миграции схемы - разовая задача, запускаемая той же сборкой и с той же конфигурацией, что и сервис:
`app migrate` накатывает новые миграции и завершается. В `docker-compose.yml` это отдельный сервис
`migrate`, а бэкенд стартует только после его успешного завершения.

Миграции версионируются (goose ведёт таблицу версий), лежат в репозитории рядом с кодом
(`backend/migrations/sql`) и встроены в бинарник.
